# Notifications

## Status

Phase 16 — implemented (`App\Domain\Notifications`).

## In-app inbox + external channels (implemented)

Every notification event creates exactly one `notifications` row
(`App\Domain\Notifications\Models\Notification`) — the in-app inbox record, always created
regardless of the recipient's channel preferences. Separately, the event best-effort fans out to
whichever external channels (`sms`/`push`/`email`/`whatsapp`) the recipient has enabled; the
`channels` column on that same row records which ones were actually attempted, for observability.

`App\Domain\Notifications\Actions\SendNotificationAction` is the single entry point for every
notification in the system. External delivery is deliberately fire-and-forget: a failed or
unavailable channel provider is caught and logged (`notifications.delivery_failed`), never allowed
to block the in-app record from being created or to bubble up and break the business action that
triggered it (an order status change, a document expiry scan).

Channel preferences live on `customers.notification_preferences` (added in Phase 5:
`sms`/`push`/`email` default `true`, `whatsapp` default `false`). A recipient with no customer
profile — a provider owner, a driver, or platform staff — has no preferences to read, so they get
the same defaults. There is no per-provider/per-driver preference customization yet; only
customers can currently change theirs (`PATCH /api/v1/customers/me`).

## Vendor adapters (implemented, all default to Log)

Every channel follows the same pattern already established for SMS/OTP delivery in Phase 1:
business code depends on an interface, never a vendor SDK directly, so a real vendor can be
swapped in later without touching `SendNotificationAction` or any of its callers.

| Channel  | Contract                                        | Config driver key         | Env var                  |
|----------|--------------------------------------------------|----------------------------|---------------------------|
| SMS      | `App\Domain\Notifications\Contracts\SmsProvider`      | `services.sms.driver`      | `SMS_PROVIDER_DRIVER`      |
| Push     | `App\Domain\Notifications\Contracts\PushProvider`     | `services.push.driver`     | `PUSH_PROVIDER_DRIVER`     |
| Email    | `App\Domain\Notifications\Contracts\EmailProvider`    | `services.email.driver`    | `EMAIL_PROVIDER_DRIVER`    |
| WhatsApp | `App\Domain\Notifications\Contracts\WhatsappProvider` | `services.whatsapp.driver` | `WHATSAPP_PROVIDER_DRIVER` |

No real vendor has credentials yet (see `docs/SECURITY.md` §Secrets), so every driver defaults to
its `Log*Provider` adapter, which writes a structured `{channel}.would_send` log line instead of
actually sending anything. An unrecognized driver value safely falls back to the log adapter
rather than silently sending nothing (`App\Providers\NotificationServiceProvider`).

## Message content

User-facing notification text is translated (`lang/ar/notifications.php`, `lang/en/notifications.php`),
resolved against the recipient's own `locale` (falling back to `config('app.locale')`) — not the
current request's locale — since a notification can be generated by a background process (the
daily expiry scan) with no request context of its own.

## Wired-up events (implemented)

- **Order lifecycle** (`App\Domain\Notifications\Listeners\SendOrderNotificationListener`,
  see `docs/ORDER_LIFECYCLE.md`):
  - `OrderCreated` → notifies the customer their order was received.
  - `OrderStatusChanged` → notifies the customer only on milestone statuses (`provider_assigned`,
    `provider_en_route`, `provider_arrived`, `completed`) — the granular in-between states
    (`vehicle_loading`, `trip_started`, `in_transit`, `vehicle_delivered`) are covered by live
    tracking (Phase 11), not a push/SMS interruption.
  - `OrderCancelled` → notifies the customer, and separately the assigned driver if one existed.
    `OrderCancelled` was changed to implement `ShouldDispatchAfterCommit` this phase — it's
    dispatched from inside `App\Domain\Orders\Actions\CancelOrderAction`'s own DB transaction, and
    a listener with a real side effect (an actual notification send) must never fire for a
    cancellation that could still roll back. This is the same reasoning already applied to every
    `ShouldDispatchAfterCommit` event in the Payments/Ledger domains — a pre-existing gap that
    only became relevant once a listener with real side effects was added.
  - `App\Domain\Orders\Listeners\LogOrderLifecycleListener` still runs too, unchanged — structured
    logging for ops/monitoring is a distinct concern from user-facing delivery, not something this
    phase replaces.
- **Document expiry** (`App\Console\Commands\CheckDocumentExpiryCommand`, see
  `docs/COMPLIANCE.md` §Expiry): the existing daily scan now also notifies whoever owns the
  expiring document — the provider's owner, or the driver themselves for a driver-owned document —
  in addition to its existing structured log line, which is unchanged (ops monitoring, not
  end-user-facing).

## Inbox API (implemented)

A single shared endpoint set — every authenticated user type (customer, provider staff, driver,
platform staff) reaches only their own notifications via the authenticated user, never a route
parameter, the same ownership shape as every other `/me` endpoint in this project:

- `GET /api/v1/notifications/me` — paginated, `?unread_only=1` filter, `meta.unread_count`.
- `POST /api/v1/notifications/me/{notificationPublicId}/read` — marks one notification read.

## Not yet in this phase

- No real vendor integration for any channel (no SMS/push/email/WhatsApp credentials exist —
  same "log adapter until Phase X" pattern as every other unconfigured external service in this
  project).
- No per-provider/per-driver notification preference customization — only customers can opt out
  of a channel today.
- No "mark all as read" convenience endpoint — only one notification at a time.
- No notifications for reviews, disputes, settlements, or payments — this phase's scope was
  bounded to the two explicitly-deferred integration points from earlier phases (order lifecycle,
  document expiry). Wiring up more event sources is straightforward
  (`SendNotificationAction::handle()` from any new listener) but wasn't asked for yet.
